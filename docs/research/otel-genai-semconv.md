# OpenTelemetry GenAI semantic conventions target

Research cutoff: 2026-08-05. Sources are limited to OpenTelemetry's official specification repositories and are pinned where possible.

## Target and stability

Target the standalone `open-telemetry/semantic-conventions-genai` registry at commit [`b694ec35855d8eccfacd5b09e4b72a808b363038`](https://github.com/open-telemetry/semantic-conventions-genai/commit/b694ec35855d8eccfacd5b09e4b72a808b363038). At this commit the registry manifest identifies itself as schema `https://opentelemetry.io/schemas/gen-ai-dev/1.42.0-dev`, has overall stability `development`, and depends on the core semantic conventions schema `1.44.0` ([manifest](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/manifest.yaml#L1-L12)). The schema URL itself was not yet published and returned 404, and the standalone repository had no published tag or release at the cutoff. `1.42.0-dev` is therefore a development identifier rather than an immutable release reference; Traicer should record both it and the commit.

The inference span and every GenAI field below are development-level conventions. The inference operation requires `gen_ai.operation.name` and `gen_ai.provider.name`; request model is conditionally required when available, while response model, finish reasons, and usage are recommended. Instructions, messages, and tool definitions are opt-in because they can be large and sensitive ([inference span](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/docs/gen-ai/gen-ai-spans.md#L33-L101)). This fits Traicer only if mandatory local secret stripping and redaction remain ahead of canonicalisation and persistence.

## Field map

| Captured meaning | OTel canonical field or structure | Mapping consequence |
| --- | --- | --- |
| Provider/system | `gen_ai.provider.name` | Use the provider known to the instrumentation, using a well-known value when applicable (`openai`, `anthropic`, `aws.bedrock`, `azure.ai.openai`, and so on). The convention explicitly allows this to differ from the actual upstream model host behind a proxy ([registry](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/registry.yaml#L3-L97)). Do not emit the obsolete `gen_ai.system`. |
| System prompt/instructions | `gen_ai.system_instructions` | This is a list of content parts only when the API supplies instructions separately; a system-role message carried in chat history stays in `gen_ai.input.messages` ([registry](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/registry.yaml#L718-L759)). |
| Operation | `gen_ai.operation.name` | For proxied chat/completion calls use the applicable well-known operation, normally `chat`, `generate_content`, or `text_completion`; tool executions use `execute_tool`. |
| Requested model | `gen_ai.request.model` | Preserve the exact provider-facing requested model name; the convention says a fine-tuned model should be more specific than its base model ([span attribute group](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/spans.yaml#L14-L25)). |
| Actual response model | `gen_ai.response.model` | Preserve the exact model reported by the provider; it may differ from the request model ([registry](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/registry.yaml#L200-L209)). |
| Token usage | `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens` | Use provider totals when available. Input includes cached tokens; cache-read and cache-creation counts are additional fields included within input total. Reasoning output tokens are additional and included within output total. Prefer billed counts when a provider exposes both billed and model-consumed counts ([registry](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/registry.yaml#L265-L310)). There is no separate `total_tokens` attribute; compute it only for display, not as an invented `gen_ai.*` key. |
| Tool definitions | `gen_ai.tool.definitions` | Encode an ordered list. Function definitions require `type: "function"` and `name`; `description` is optional and `parameters`, when present, is JSON Schema draft-07 ([tool-definition schema](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/gen-ai-tool-definitions.json#L1-L84)). |
| Tool request/result in model messages | Message parts `type: "tool_call"` with `id`, `name`, `arguments`, and `type: "tool_call_response"` with matching `id`, `response` | These parts preserve the model-visible request/result in message order ([input schema](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/gen-ai-input-messages.json#L412-L485)). |
| Executed tool invocation | A child/internal `execute_tool` span with `gen_ai.tool.name`, optional `gen_ai.tool.call.id`, `gen_ai.tool.type`, `gen_ai.tool.description`, `gen_ai.tool.call.arguments`, and successful `gen_ai.tool.call.result` | The span name is `execute_tool {gen_ai.tool.name}`. Arguments and results are structured objects where possible and are opt-in/sensitive ([execute-tool span](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/docs/gen-ai/gen-ai-spans.md#L1045-L1126)). A canonical record that cannot express child spans can retain the model-visible parts, but must not collapse an observed execution into a definition. |
| Finish reason | `gen_ai.response.finish_reasons` and each output message's `finish_reason` | The span attribute is an array aligned with generations. Each output choice also requires one finish reason; well-known message-schema values are `stop`, `length`, `content_filter`, `tool_call`, `compaction`, and `error`, while provider-specific strings remain allowed ([registry](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/registry.yaml#L210-L216), [output schema](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/gen-ai-output-messages.json#L144-L156)). |
| Input/output content | `gen_ai.input.messages`, `gen_ai.output.messages` | Input is an ordered array of `{role, parts, name?}`; output is an ordered array of `{role, parts, name?, finish_reason}` with exactly one message per choice. Roles have well-known values `system`, `user`, `assistant`, and `tool`. Parts may be text, tool call/request, server-side tool call/request, blob, file, URI, reasoning, compaction, or a typed extension ([input schema](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/gen-ai-input-messages.json#L52-L127), [output schema](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/gen-ai-output-messages.json#L215-L304)). Input messages must remain in send order, and each output message represents exactly one choice ([registry](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/registry.yaml#L760-L848)). |

The convention permits these complex attributes to be structured values, but when a span API cannot carry structured attributes it recommends a JSON string on spans and structured form on events ([content recording](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/docs/gen-ai/gen-ai-spans.md#L1211-L1235)). Traicer's canonical form should remain the structured OTel-shaped value; JSON-string encoding belongs only at an OTLP/export boundary, otherwise a nested JSON value can be double-encoded and hashed differently depending on ingest path.

## Outcome does not have a generic OTel home

There is no natural OTel GenAI attribute for a marketplace-level task outcome such as success/failure, accepted/rejected, or a domain-specific result label. `gen_ai.response.finish_reasons` says why model generation stopped, and `gen_ai.response.status` is the provider-reported generation lifecycle (`queued`, `in_progress`, `completed`, `incomplete`, `failed`, or `cancelled`); neither means the agent completed the user's task correctly ([response fields](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/registry.yaml#L210-L256)).

`gen_ai.evaluation.score.label` can carry labels such as `pass` or `fail`, but only as the result of a named evaluation. The `gen_ai.evaluation.result` event requires `gen_ai.evaluation.name` and attaches the score label/value to a response or parent operation ([evaluation event](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/events.yaml#L14-L39), [evaluation attributes](https://github.com/open-telemetry/semantic-conventions-genai/blob/b694ec35855d8eccfacd5b09e4b72a808b363038/model/gen-ai/registry.yaml#L849-L873)). Use it when Traicer records a real evaluator and metric. Otherwise keep marketplace outcome under an explicit Traicer namespace, for example `traicer.outcome`, and do the same for task/domain labels rather than inventing `gen_ai.*` keys.

## Deterministic serialization implications

OpenTelemetry specifies semantic fields and JSON shapes, not byte-level canonical JSON. The schemas permit additional properties and many optional fields, while the convention requires array order for messages and choice correspondence. Traicer therefore needs one serialization profile above the OTel shape:

1. Recursively sort object/attribute keys by one documented string ordering, but preserve every array's input order, including messages, content parts, output choices, finish reasons, and tool definitions.
2. Omit unavailable optional fields. Do not materialize schema `default: null` values; retain `null` only when it was explicitly observed and the schema permits it, so missing input does not acquire new bytes during a decode/encode round trip.
3. Accept JSON-finite numbers only and emit one documented shortest base-10 representation, normalizing negative zero to zero. Token counts remain integers.
4. Canonicalise structured values, including tool arguments/results and JSON Schema parameters, rather than their provider-supplied JSON text. Parse those strings before redaction/canonicalisation when safe; if parsing fails, preserve the value as an ordinary string without pretending it is the structured OTel field.
5. Serialize once after mandatory secret stripping and redaction, then hash and encrypt exactly those bytes. OTLP's allowed JSON-string fallback must be decoded back into the same structured form before this step.

These are Traicer rules, not claims that OTel defines a canonical wire encoding. Their consequence is that equivalent OTLP structured attributes and JSON-string fallbacks converge on the same canonical bytes, while meaningful array order and the distinction between absent and explicitly null values survive.
